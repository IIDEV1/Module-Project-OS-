# Проект №3 — Анализ журналов веб-сервера (все блоки A → B → C)

**Дисциплина:** Проектирование операционных систем, модуль 1 (РК-1).  
**Группа:** CS 32-24 
**Команда / жеребьёвка:** 3



## Цель проекта

За неделю покупатели интернет-магазина жаловались на сбои оплаты. Требуется обработать **40 файлов по 15 000 запросов** и определить, в каком файле, по какому пути и когда происходили ошибки. Для скорости используем несколько дочерних процессов Linux.

Формат строки журнала:

```text
2026-10-20 02:00:00 10.0.3.227 POST /api/orders 200 303ms
```

`2026-10-20` — дата, `02:00:00` — время, `10.0.3.227` — IP, `POST` — метод, `/api/orders` — URL-путь, `200` — HTTP-код ответа, `303ms` — длительность.

**5xx** — коды 500–599: сервер не смог нормально обработать запрос.

## Структура единого проекта

```text
modul1/
├── README.md          # эта инструкция: запуск, результаты, выводы
├── errors.sh          # блок A: Bash (требование преподавателя)
├── project3.py        # единый Python-файл для блоков A, B и C
├── run_all.sh         # ЕДИНАЯ команда запуска всего проекта
├── logs/
│   ├── access_01.log
│   ├── ...
│   └── access_40.log
└── reports/            # выводы, CSV, JSON и результаты strace после запуска
```

Файлы журнала взяты из предоставленного `logs.zip`, без изменений.

## Быстрый запуск в Ubuntu / WSL2

Условия: **Ubuntu / WSL2**, **Python 3.11+**, Bash, `ps`, `wc`, `awk`, `strace` (для экспериментов со системными вызовами). `gcc` не требуется для этого конкретного решения, потому что блок C реализован на Python.

Если проект скачан ZIP-файлом в стандартную папку Windows `Downloads`, в терминале **Ubuntu WSL**:

```bash
cd ~
unzip /mnt/c/Users/user/Downloads/modul1_project3_ABC.zip -d ~
cd ~/modul1
bash run_all.sh
```

> Если Windows-пользователь или путь к `Downloads` другой — поправьте его. Если `unzip` / `strace` отсутствует: `sudo apt-get update && sudo apt-get install -y unzip strace`.

**Одна команда сдачи/демонстрации:**

```bash
bash run_all.sh
```

Она последовательно запустит блок A, блок B с 1, 2 и 4 процессами, блок C тремя методами обмена, сравнит результаты, проверит PID после `waitpid`, запишет текст, CSV и JSON в `reports/` и, если есть `strace`, снимет его статистику. **На компьютере преподавателя/в WSL время будет другим.**

## Блок A — базовый (Bash + strace)

Задание: `errors.sh` подсчитывает количество строк и 5xx в **каждом** файле, печатает общие суммы и файл с максимальным числом 5xx.

```bash
bash errors.sh
```

Пример итоговых строк для приложенного набора:

```text
ИТОГО: 600000 строк, 2580 ошибок 5xx
Больше всего 5xx: access_17.log (149 ошибок)
```

Проверка `strace -c` для `wc -l` и собственного Python-подсчёта одного файла:

```bash
strace -c -o reports/A_wc_strace.txt wc -l logs/access_01.log
strace -c -o reports/A_python_strace.txt python3 project3.py a --file logs/access_01.log
cat reports/A_wc_strace.txt
cat reports/A_python_strace.txt
```

Сравните **три самых частых системных вызова по столбцу `calls`** (их реальные названия и количества после запуска будут выписаны в `reports/A_top3_syscalls.txt`). В `wc -l` работает небольшая C-программа; Python выполняет больше системных операций при запуске интерпретатора и загрузке модулей (например, `openat`, `newfstatat`, `mmap`), а затем читает строки в цикле. Точное распределение системных вызовов зависит от версии Linux, Python и `strace`. Сам `strace` также увеличивает время работы программы.

`errors.sh` содержит shebang `#!/usr/bin/env bash`, переменные Bash заключены в кавычки; файлы считаются с помощью `wc` и `awk`.

## Блок B — основной (fork + pipe)

1. Родитель создаёт N дочерних процессов через `os.fork()`.
2. Каждый ребёнок обрабатывает **свои** файлы (`files[i::N]`).
3. Каждый подсчитывает число запросов и 5xx по файлам и по путям.
4. Каждый отправляет результат родителю через `os.pipe()`.
5. Родитель читает результаты, вызывает `os.waitpid()` для **каждого** PID, объединяет статистику, сохраняет CSV и проверяет `ps`.

Команды:

```bash
python3 project3.py b -n 1
python3 project3.py b -n 2
python3 project3.py b -n 4
```

Готовые отчёты: `reports/b_pipe_n1`, `reports/b_pipe_n2`, `reports/b_pipe_n4`. Там три CSV: `files.csv` (каждый файл), `paths.csv` (каждый путь), `files_paths.csv` (каждая комбинация), а также `result.json`.

### Фактические результаты на приложенных файлах

- Всего запросов: **600 000**.
- Всего 5xx: **2 580** (**0,43%**).
- Наибольшее **число** 5xx: **access_17.log — 149**.
- Наихудшая доля по конкретной комбинации: **`access_17.log` + `/api/payment` — 97 из 587 (**16,52%**)**.
- Во всех трёх запусках данные полностью совпали.

В качестве **примера** измерения, выполненного при тестировании этой сборки (не гарантия результата на другом ноутбуке):

| N процессов | Время, сек |
|---:|---:|
| 1 | 0,5763 |
| 2 | 0,4396 |
| 4 | 0,2519 |

Время — wall-clock от запуска `fork` до получения, чтения и ожидания дочерних процессов. На одном конкретном измерении 4 процесса оказались быстрее, но параллелизм не всегда ускоряет работу — зависит от диска, CPU, нагрузки.

В терминале после `waitpid()` есть проверка:

```text
Проверка ps после waitpid:
    PID    PPID STAT CMD
Зомби этих PID: НЕТ
```

Зомби — это завершившийся процесс, статус которого ещё не прочитан родителем. `waitpid` забирает статус и удаляет запись процесса из таблицы процессов.

## Блок C — продвинутый (три способа IPC)

Три запуска с одинаковой задачей и количеством процессов:

```bash
python3 project3.py c --method pipe -n 4
python3 project3.py c --method shm -n 4
python3 project3.py c --method file -n 4
```

- **`pipe`** — передача JSON по файловому дескриптору `os.pipe()`.
- **`shm`** — `multiprocessing.shared_memory.SharedMemory`, размер и JSON передаются через общий буфер памяти. Родитель вызывает `close()` и `unlink()`.
- **`file`** — каждый дочерний процесс записывает результат в отдельный файл во временном каталоге; родитель читает их после `waitpid`, затем удаляет временный каталог.

**`strace -f -c`** по каждому методу собирается через `bash run_all.sh` (флаг `-f` необходим для отслеживания дочерних процессов). Отчёты: `reports/C_pipe_strace.txt`, `reports/C_shm_strace.txt`, `reports/C_file_strace.txt`; по каждому отдельно сохраняются 3 наиболее частых системных вызова. До запуска с установленным `strace` этих файлов не будет — не нужно придумывать цифры.

### Найденные начало и конец сбоя оплаты

В файле `access_17.log`:

```text
Путь: /api/payment
Ошибок 5xx в файле по этому пути: 97 из 587 (16,52%)
Основной плотный кластер: 96 ошибок 5xx
Начало наблюдаемого всплеска: 2026-10-21 10:47:05
Конец наблюдаемого всплеска: 2026-10-21 11:22:36
```

В файле есть **одна отдельная ошибка в 10:01:25**, но она не входит в основной всплеск. Программа разделяет группы ошибок паузой **более 5 минут**. Таким образом, времена — **границы наблюдаемого в логах всплеска**, а не доказательство точного технического момента начала/устранения сбоя.

### Ctrl+C и очистка ресурсов

Чтобы успеть нажать Ctrl+C, предусмотрена учебная искусственная задержка:

```bash
python3 project3.py c --method shm -n 4 --slow 10
```

Пока программа работает, нажмите **Ctrl+C**. Родитель перехватывает `KeyboardInterrupt`, отправляет сигнал детям, вызывает `waitpid` и удаляет свои сегменты в `/dev/shm`. Ожидаемое сообщение:

```text
Ctrl+C: дочерние процессы остановлены; waitpid и очистка выполнены.
```

Сразу после этого можно проверить:

```bash
ps -eo pid,ppid,stat,cmd | grep '[p]roject3.py'
ls /dev/shm/psm_* 2>/dev/null || echo "Нет psm_*"
```

Примечание: другие программы в системе могут иметь собственные `psm_*`; наш процесс удаляет только свои. Проверка в обычном запуске печатает отдельную строку `Остатки собственных сегментов /dev/shm: НЕТ`.

## Основные выводы для сдачи

1. **Проблемный сервис:** `/api/payment` (оплата заказов); главный всплеск локализован в `access_17.log`.
2. **Проблемный временной интервал:** 21.10.2026, с 10:47:05 до 11:22:36 по записям с 5xx.
3. **Параллелизм:** родитель делит файлы на части, процессы работают одновременно, затем родитель получает результаты; при N=4 в одном замере получилось быстрее, чем при N=1.
4. **IPC:** pipe — поток байтов; shared memory — общий буфер; временные файлы — обмен через файловую систему.
5. **Зомби и утечки:** `os.waitpid()` собирает дочерние PID, `shm.unlink()` удаляет shared memory, `TemporaryDirectory.cleanup()` удаляет временные файлы.
6. **Результаты:** у всех способов одинаковые подсчёты; сравнение `strace` доступно только после его реального запуска.

## Частые вопросы преподавателя

**Что такое `fork()`?** Создаёт дочерний процесс, который начинает исполнять код после вызова `fork`. У родителя он возвращает PID ребёнка, у ребёнка — 0.

**Что такое `pipe()`?** Канал, из которого один процесс читает байты, а другой записывает их. В Python это файловые дескрипторы для чтения и записи.

**Что делает `waitpid()`?** Дожидается окончания конкретного дочернего процесса и забирает его код завершения; это предотвращает зомби.

**Почему 5xx, а не 4xx?** 5xx означает ошибку на стороне сервера; 4xx обозначает ошибки запроса/доступа на стороне клиента в терминах HTTP.

**Как вычисляется доля?** `число 5xx / общее число запросов * 100%`.

**Что делает `strace -f -c`?** Отслеживает системные вызовы процессов и потом показывает сводку по их количеству/времени; `-f` добавляет дочерние процессы, `-c` суммирует статистику.

**Почему основной сбой не начинается в 10:01:25?** Это одиночная ошибка, отдельно от плотной серии; мы ищем устойчивый кластер из 96 ошибок, а не самую первую разрозненную запись 5xx.

**Почему всё в одном проекте, но два кода?** Все блоки A/B/C объединены в `project3.py`, однако блок A дополнительно **обязательно** требует самостоятельный Bash-файл `errors.sh`. Поэтому сдаётся **один архив**, а не три разных проекта.
